# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

QGIS plugin (Python / PyQt5) that talks to the ANYWAYS API stack to plan routes, manage projects, and upload/download trip datasets. Loaded by QGIS via `__init__.py:classFactory`. The plugin id is `anyways_impact_toolbox`; the user-facing menu name is `&ANYWAYS`.

The plugin's official Notion subpage is https://www.notion.so/33cd073d113e81d4a4d3eb3a76a17c01 — treat that as the canonical "what is this" reference; this file documents *how to work on the code*.

## Build, deploy, run

The toolchain is `pb_tool` plus the standard PyQt5 compilers. There is no test suite.

```bash
# install once
pip3 install pb_tool

# regenerate dialog Python from Qt Designer .ui
pyuic5 --import-from=. -o ImPact_toolbox_dialog_base.py ImPact_toolbox_dialog_base.ui

# regenerate resources.py (only needed when icons / .qrc change)
pyrcc5 -o resources.py resources.qrc

# compile + zip + deploy into the local QGIS profile
pb_tool compile && pb_tool zip && pb_tool deploy --no-confirm
```

`pb_tool.cfg` is the deployment manifest. **Anything you add at the top level — a new Python file or a new subdirectory — must be listed there (`python_files` or `extra_dirs`) or it will not ship.** CI uses the same `pb_tool compile` / `pb_tool zip` flow (see `.github/actions/build-plugin/action.yml`).

`metadata.txt` holds `version=` (the source of truth for the plugin version, also read at runtime by `ApiClient._read_plugin_version`) and the `experimental=` flag. CI flips `experimental=True` on the `develop` branch via `sed`.

Inside QGIS, runtime feedback goes to two places:
- `print()` → Plugins → Python Console
- `QgsMessageLog.logMessage(..., MESSAGE_CATEGORY, ...)` → View → Panels → Log Messages, "ANYWAYS" tab

The README mentions a debugging convention: an exception with message `FIRST AID!` is rethrown so the First Aid plugin can catch it.

## Translations

Strings inside `.ui` files are picked up automatically; in Python wrap user-visible strings in `self.tr(...)`. Workflow:

```bash
pylupdate5 -verbose *.ui *.py -ts i18n/ImPact_toolbox_en.ts i18n/ImPact_toolbox_nl.ts   # extract
# edit .ts files in Qt Linguist
cd i18n && lrelease *.ts                                                                  # compile to .qm
```

## Architecture

### Entry points and the dialog
- `__init__.py:classFactory` → `ImPact_toolbox.py:ToolBox` (registers menu/toolbar action and a "Upload to ANYWAYS..." context-menu action on vector layers).
- `ToolBox.open_dialog` constructs `ImPact_toolbox_dialog.py:ToolBoxDialog`, which is the entire main UI. The .ui file (`ImPact_toolbox_dialog_base.ui`) is loaded at runtime via `uic.loadUiType`; the generated `ImPact_toolbox_dialog_base.py` exists for IDEs and is regenerated by the `pyuic5` command above.
- `upload_dataset_dialog.py:UploadDatasetDialog` is a small modal used by the layer-tree "Upload to ANYWAYS..." action.

### Three distinct API clients (do not confuse)
All live under `clients/` and all take an optional `get_token` callable that returns a bearer token:

| Client | Base URL setting | Purpose |
|---|---|---|
| `clients/api/ApiClient` | `API` (`https://api.anyways.eu/impact/`) | Projects-API v3.0. `POST /v3.0/data/` for project/dataset lookups (flat array of typed objects, filtered by `_type`), `PUT /v3.0/data/` for dataset upload, `POST /v3.0/track` for usage tracking. |
| `clients/edit_api/EditApiClient` | `EDIT_API` (`https://api.anyways.eu/edit/`) | Resolves a `branch_id` to its latest `commit_id` via `GET branch/{id}`. Used as the first step before routing. |
| `clients/publish_api/PublishApiClient` | `API` | Routing. `POST /v3.0/cachedroutes/{commit_id}` returns either the full result or a `batch` token; the client polls `GET /v3.0/cachedroutes/{commit_id}/batch/{batch}` until `batch` is null, accumulating routes via `AdHocRoutesResponse.merge`. |

`settings.py` is the single source for endpoint URLs and OIDC config. Do not hardcode URLs elsewhere.

### Auth
- `auth/DeviceFlowAuth.py` runs the OIDC device-authorization flow against `OIDC_AUTHORITY`. It uses `QTimer` to poll the token endpoint (Qt-friendly, no threads), and emits `token_received` / `login_failed` / `logged_out` signals.
- `auth/TokenStorage.py` persists `access_token` / `refresh_token` / `expires_at` in `QgsSettings` under `anyways.eu/impact/auth/`.
- `_refresh_token` **only clears storage on an explicit `invalid_grant`** — every other failure (network, 5xx, etc.) leaves tokens intact so the next attempt can retry. Don't change this without thinking through offline / flaky-network UX.
- `ApiClient.track` is fire-and-forget on a background thread and reads the token directly from `TokenStorage` instead of going through `get_token`. This is intentional: tracking must never trigger a refresh, never block, and never raise. Preserve those properties when editing it.

### Routing pipeline
1. `ToolBoxDialog.run_routeplanning` builds a `Matrix` either from a line layer (`RoutingHandler.build_matrix_from_lines`) or two point layers (`build_matrix_from_points`). Line layers can carry a per-feature `profile` attribute that overrides the global profile picker — the dialog detects this via `fields().indexFromName("profile")` and disables the picker accordingly.
2. `RoutingHandler.start_route_planning` wraps a `RoutingTask` (a `QgsTask` subclass) and hands it to `QgsApplication.taskManager()`. The task is appended to the class-level `RoutingTask.RUNNING_TASKS` list to keep it alive (Qt would otherwise GC it).
3. The task resolves branch → commit via `EditApiClient`, then calls `PublishApiClient.post_ad_hoc_routes`, which handles the batch-polling loop. Progress goes back to `QgsTask.setProgress` via the `on_progress` callback.
4. On completion, `routes_planning_callback` builds three layers via `layers/SegmentsLayerBuilder`, `RoutesLayerBuilder`, `ErrorLayerBuilder`, groups them in the layer tree, and styles them with `impact/default_layer_styling.py`. Color/offset come from `PROFILE_COLOURS` / `PROFILE_OFFSET` in `settings.py`, keyed by the *prefix* of the profile name (e.g. `bicycle.fast.5%` → `bicycle`).

### Persistent state
- Project-level state (selected project id, last network/profile/layer pickers) is stored in the QGIS `.qgs` project file via `QgsProject.instance().writeEntry("anyways", ...)`.
- `impact/previous_state_tracker.py:previous_state_tracker.init_and_connect` wires QComboBoxes to that storage. The `extra_state_from` parameter lets one combobox's state be keyed by another's value (e.g. profile-per-network).
- An in-memory `_project_cache = {"projects": ...}` dict is shared between `ToolBox` (for the layer-tree upload action) and `ToolBoxDialog`, so the project list isn't re-fetched per-dialog-open.

### Tracking events
The plugin posts events to `/v3.0/track` (see README "Usage tracking" section for the user-facing list). Action names currently in use: `project.open`, `project.error`, `network.route`, `network.error`, `dataset.open`, `dataset.create`, `dataset.error`. Errors carry a `stack` property with `traceback.format_exc()`. Keep that pattern when adding new error paths.

## Conventions

- Logging: `QgsMessageLog.logMessage(msg, MESSAGE_CATEGORY, Qgis.Info|Warning|Critical)`. `MESSAGE_CATEGORY = "ANYWAYS"`.
- `staging_mode` in `impact/__init__.py` is a manual flag — flipping it shows a warning banner; it is *not* wired to a different API endpoint, so changing endpoints means editing `settings.py`.
- Coordinate handling: layers are transformed to EPSG:4326 (`transform_layer_to_wgs84` in `layers/PointLayerHelpers.py`) before being sent to the API.
- The line-layer convention is: `count` (forward trip count), optional `count_rev` (reverse), optional `profile` (per-feature profile override). See `RoutingHandler.build_matrix_from_lines`.
- Profile keys are the hardcoded list in `ImPact_toolbox.py:ToolBox.__init__` (`profile_keys`). Adding a new profile means editing that list and likely `PROFILE_COLOURS`/`PROFILE_OFFSET` too.

## CI / release

- `.github/workflows/staging.yml` — push to `develop` → builds with `experimental=True`, publishes a prerelease GitHub release tagged `latest`, and uploads to the QGIS plugin repo.
- `.github/workflows/production.yml` — production release flow.
- Releases on the QGIS repo are uploaded by `deployment/plugin_upload.py` (XML-RPC to `plugins.qgis.org`).
